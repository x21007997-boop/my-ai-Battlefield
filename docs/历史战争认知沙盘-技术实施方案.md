# 历史战争认知沙盘：技术实施方案

## 0. 项目定位

本项目明确是在制作一款游戏：玩家扮演历史战争中的军队指挥官，在连续时间中下达命令，接收延迟且可能失真的情报，并承担由此产生的战场后果。

因此，后续所有研发计划都以最终可玩的游戏为判断标准：规则、数据、引擎、地图、界面、音效、反馈和回放都应围绕“玩家是否能形成决策—等待—判断—修正—承担后果”的游戏循环建设。

当前 React/Vite 版本是规则验证、战役数据编辑和过渡性沙盘，不是最终产品形态。正式游戏客户端引入 Godot 作为运行和表现层；战场规则、历史剧本包、回放事件和指挥官认知投影继续保持引擎无关。

### 0.1 原型与正式项目边界

仓库中同时存在两条产品线，必须分开验收：

1. **既有原型**：`src/prototype/political/`、`scenarios/hongguang-1645/` 和 `scenarios/yangzhou-1645/`，是弘光元年的月度政治决策推演原型。它可以继续运行，但不承担实时战场规则，也不代表正式战争游戏已经完成。
2. **正式项目**：`src/battlefield/`、`scenarios/changping-260/` 和 `godot/`，是基于历史背景的实时战争推演游戏。正式验收必须检查 Godot 客户端中的战役闭环、命令延迟、非完全情报、敌方认知和战后结果。
3. **迁移期浏览器原型**：`src/prototype/battlefield/BattlefieldPrototype.jsx` 用于快速验证正式项目的规则和交互，不得成为另一套独立规则来源，也不能替代 Godot 正式客户端。

两条产品线的世界状态、规则入口、剧本格式和里程碑不得混用。原型测试通过，只能说明原型或迁移验证面可用；正式项目完成必须以正式客户端可玩为准。

正式游戏客户端从独立目录开始建设：

```text
godot/
├── project.godot          Godot 游戏工程
├── scenes/Main.tscn       战场主场景
├── scripts/main.gd        连续时间与指挥输入垂直切片
├── scripts/sand_table.gd  沙盘图层渲染
├── data/                  从 scenarios/ 生成的客户端数据
└── assets/                游戏运行所需资源
```

`scripts/export-godot-scenario.mjs` 是历史剧本到游戏客户端数据的单向生成入口。Godot 不直接修改历史剧本，也不把场景节点当作战场真值。

当前 Godot 正式客户端已经包含第一层游戏交互：点击我方旗帜选中部队，点击区域选择目标，命令进入传递状态；鼠标滚轮缩放沙盘，中键拖拽镜头。下一阶段应把这些交互继续扩展为正式战役内容，并始终接入统一的命令事件和回放事件，而不是在 UI 内增加独立规则。

Godot 客户端现在使用 `event_log.gd` 记录指挥官可见事件，并支持导出 `user://changping-replay.json`。通用核心中的 `src/battlefield/replay.js` 与 Godot 的 `replay_player.gd` 共同遵守同一份指挥官回放协议：回放事件禁止写入 `actualAreaId`、敌军真实位置、战斗交换和其他未经玩家获知的真值；客户端从事件流重建玩家视角，而不能重新读取完整世界状态。Godot 当前已支持载入上一局回放、按时间轴跳转和播放。

通用内核新增 `resolution.js`。胜负条件由战役包的 `simulation-parameters.json.resolution` 提供，内核只负责按规则评估并写入 `battle_ended` 事件；客户端只消费结果。长平是正式可玩的第一张战役关卡；场景包中的 `experimental` 只表示史料或模拟参数仍在治理中，胜利条件是游戏规则，不应叙述为已经被史料证明的历史因果。

Godot 初始化数据现在通过 `commanderSession` 输出。它由 `buildCommanderSessionSnapshot` 生成，统一包含指挥官地图投影、我方命令、我方侦查状态和 `payload` 形状的安全事件流；Godot 不再独立拼装首屏态势。后续实时接入只允许传递这份会话契约，不能把完整世界状态下发给客户端。

当前已增加 `commanderGateway.js` 和 `battle-engine-server.mjs`：网关接受移动、坚守、侦查、取消命令和时间推进请求，调用通用内核后返回安全会话。Godot 通过 `engine_gateway.gd` 可选接入该网关；未配置网关地址时仍使用本地垂直切片，作为迁移期回退路径。

每个阶段必须至少满足以下一项：

- 增强玩家的指挥与决策体验；
- 增强实时战场、信息不对称或后果反馈；
- 增加正式游戏客户端的可玩内容；
- 提高战役、回放或多平台发布能力。

单纯增加资料、替换框架或美化界面但不改善游戏循环，不单独作为产品里程碑。

## 1. 实施目标

本方案把《历史战争认知沙盘-详细方案》转换为可以逐步提交、测试和回滚的研发任务。

第一条技术纵线只验证三个最重要的风险：

```text
连续时间推进
→ 命令不会瞬间生效
→ 玩家只能读取自己的认知视图
```

第一阶段不接入完整长平史实数据，不先制作完整战斗动画，也不让大模型进入实时循环。先建立一个不依赖具体战役的 `battlefield` 领域内核，并用明确标记为内部验证用的最小战场夹具验证它；随后用长平的历史背景和可追溯初始条件接入正式可玩的实时战役关卡。目标是建立“历史背景 → 实时推演 → 历史分歧”的正式游戏循环，不是先完成一套历史资料库。

现有弘光政治模拟继续使用 `src/prototype/political/simulation.js` 和原有剧本格式，不在第一阶段改写，避免新领域破坏当前可运行的政治决策模式。

## 5. 核心接口

### 5.1 `world.js`

```js
createBattleWorld(config)
cloneBattleWorld(world)
appendBattleEvent(world, event)
```

要求：

- 不修改输入对象；
- 初始认知状态只包含己方部队，不泄露敌方真实位置；
- 所有新增状态必须能够被 JSON 序列化；
- 不依赖 React 或浏览器 API。

### 5.2 `orders.js`

```js
findRoute(areas, fromAreaId, toAreaId)
issueOrder(world, draft, options)
cancelOrder(world, orderId)
```

第一阶段支持的命令：

```js
{
  type: 'move',
  unitId: 'player-wing',
  targetAreaId: 'valley',
  priority: 'normal',
  constraints: []
}
```

`issueOrder()` 只把命令放入传递队列，不直接移动部队。

### 5.3 `clock.js`

```js
stepBattle(world, seconds = 1)
advanceBattle(world, seconds, options)
```

第一阶段每秒执行：

1. 推进模拟时间；
2. 送达达到时间的命令；
3. 执行已送达的移动命令；
4. 完成到期的侦察报告；
5. 写入状态变化事件；
6. 返回新的不可变世界快照。

核心引擎不使用 `setInterval` 或 `requestAnimationFrame`。UI 层未来可以用它们驱动调用，但规则内核必须可以在 Node 测试环境中单独运行。

### 5.4 `perception.js`

```js
queueObservation(world, observationDraft)
applyObservation(world, observation)
viewBelief(world, side)
```

`viewBelief()` 的返回值必须是脱敏视图：

- 可以包含己方部队的精确状态；
- 可以包含敌方已知或推测的 sightings；
- 不得包含敌方未被观察到的真实单位对象；
- 不得把完整 `world.units` 作为字段返回；
- 不得把内部真实观察字段透传给 AI。

### 4.3 沙盘呈现契约

沙盘不是战场真值的可视化，而是“静态地标 + 我方已知状态 + 前线报告”的认知界面。地图渲染必须遵守以下分层：

1. `presentation.mapMarkers` 提供营垒、壁垒、关口、道路、河谷和高地等静态符号；这些内容也要标注史实、估计或场景假设。
2. 我方部队可以用旗帜或军旗精确显示，因为它属于指挥官可确认的己方状态。
3. 敌军不能从 `world.units` 直接绘制，只能从 `belief.sightings` 绘制带可信度、来源和时间的疑似旗帜。
4. 内核中的 `engagements`、`combat_exchange` 和敌军真实移动不能直接投影到沙盘；必须转换为延迟送达、可能错位的 `frontline-report` 后才进入玩家视图。
5. “发现敌情”“疑似交战”和“敌军主力”是情报判断，不是地图真值。界面应通过问号、虚线、低可信标签或模糊范围表达不确定性。

因此，沙盘上可以看到“某方向疑似有敌情”，但不应直接看到敌军正在掉兵、双方正在交换伤害，或敌军真实单位已经进入某个区域。

### 4.4 基础接口冻结与开源工具边界

为避免后续更换地图组件时重写战场规则，第一阶段先冻结以下接口：

- `geography.areas[].position` 统一使用 `normalized-2d` 坐标，范围为 `0—100`；
- `presentation.map` 只描述坐标系、边界和背景资源，不承载战斗规则；
- `buildCommanderMapModel(world, options)` 是地图渲染的唯一输入适配层；
- 地图组件只能消费 `landmarks`、`friendlyUnits`、`reportedEnemySignals` 和 `routes`，不得读取 `world.units` 中的敌军单位；
- Leaflet、Pixi 或其他开源渲染器只能放在 UI 适配层，不能进入 `src/battlefield/` 的规则内核。

这样后续接入开源地图能力时，只替换“模型到画布”的适配器，不改变命令、侦察、欺骗、战斗和 AI 的数据语义。

## 6. 命令与时间语义

### 6.1 命令生命周期

```text
issued
→ transmitting
→ executing
→ completed
```

异常状态：

```text
cancelled
blocked
lost
partially_executed
```

第一阶段只需要实现 `transmitting`、`executing` 和 `completed`，但数据结构预留异常状态。

### 6.2 移动语义

路径由区域连接图计算：

```text
起点 → 中间区域 → 目标区域
```

路径成本由连接边的 `travelSeconds` 相加。第一阶段不处理复杂寻路，只使用 BFS 找到最短可达路径。

### 6.3 延迟语义

命令延迟由调用方提供：

```js
issueOrder(world, order, { delaySeconds: 3 })
```

后续由距离、道路、昼夜、通信和将领能力计算出延迟。第一阶段允许测试显式传入延迟，以便稳定验证。

### 6.4 取消和覆盖

第一阶段暂不实现复杂的命令冲突解决，但必须保留：

- 原命令记录；
- 取消时间；
- 取消原因；
- 新命令与旧命令的关联。

这保证战后可以解释“为什么部队没有执行原计划”。

## 7. 认知隔离与情报语义

### 7.1 真实观察和报告内容分开

一条侦察观察内部可能知道真实目标位置，但对玩家只产生报告：

```js
{
  targetUnitId: 'enemy-main',
  actualAreaId: 'valley',
  reportedAreaId: 'north',
  confidence: 'medium',
  observedAt: 20,
  arrivesAt: 25
}
```

后续计策系统可以让 `reportedAreaId` 与 `actualAreaId` 不同。第一阶段先支持字段隔离和延迟送达，不实现自动欺骗算法。

### 7.2 Belief State 只保存已知信息

玩家的认知状态保存：

- 自己的精确单位状态；
- 已收到的敌方 sighting；
- 报告时间；
- 可信度；
- 信息来源；
- 信息新鲜度；
- 过去报告的历史。

不保存：

- 敌方未观察单位的真实位置；
- 未发生的事件；
- 模拟器内部随机状态；
- 未对玩家公开的敌方命令。

### 7.3 AI 输入边界

未来服务端接口必须改成：

```js
{
  scenarioContext,
  beliefState,
  visibleReports,
  availableOrders,
  question
}
```

不得直接传：

```js
{
  world,
  allUnits,
  allOrders,
  hiddenObservations
}
```

## 8. 测试策略

### 8.1 单元测试

第一阶段至少覆盖：

1. 初始世界能正确生成；
2. 无效区域不能发布移动命令；
3. 命令发布后不会立即移动；
4. 命令送达后才开始执行；
5. 到达行程时间后部队进入目标区域；
6. 侦察报告在送达前不会进入 Belief State；
7. `viewBelief(player)` 不包含未发现敌军的真实单位；
8. 相同种子和命令序列能够复现；
9. 输入世界不会被修改；
10. 事件日志包含命令发布、送达和完成事件。

### 8.2 认知隔离测试

使用一个敌军真实位于 `valley`、但报告称其位于 `north` 的夹具，验证：

- World State 仍然记录 `valley`；
- 玩家 Belief State 只记录 `north`；
- 玩家视图没有敌方单位真实对象；
- 报告送达前玩家没有该 sighting；
- 复盘接口未来可以读取真实字段，但普通玩家接口不能读取。

### 8.3 回归测试

新增战场测试必须接入 `npm test`，同时运行：

```bash
npm test
npm run test:e2e
npm run build
npm run test:sites
```

现有弘光测试必须继续全部通过。

## 9. 分阶段研发任务

### Sprint 1：基础内核

目标：让一个最小战场连续运行。

- 创建 `src/battlefield/`；
- 实现世界初始化；
- 实现区域图；
- 实现部队对象；
- 实现固定时间推进；
- 实现事件日志；
- 增加 Node 测试。

### Sprint 2：命令传递

## 10. 研发完成标准

第一条技术纵线完成的标准：

- `createBattleWorld()` 能生成可序列化战场；
- `issueOrder()` 能创建有延迟的命令；
- `stepBattle()` 能连续推进时间；
- 部队不会在命令送达前移动；
- 部队会在移动成本满足后到达；
- 报告会延迟进入 Belief State；
- 玩家视图不会泄露未发现敌军真实位置；
- 事件日志可以描述整个过程；
- 同一输入可以复现；
- 现有弘光测试、浏览器测试、构建和 Sites 测试不受影响。

第一条产品纵线完成的标准：

```text
玩家看到沙盘
→ 下达移动命令
→ 看到命令传递中
→ 等待战场推进
→ 收到一份延迟战报
→ 发现地图上的敌情只是自己的认知
```

## 11. 当前研发决策

1. 不把战争规则写进当前弘光政治规则；
2. 不把未经核验的长平兵力和路线标成历史事实；可以在独立的 `scenario_assumption` 层提供可回放的实验参数；
3. 不让 AI 直接读取完整 World State；
4. 不把实时模拟绑定到 React 渲染循环；
5. 不用动画代替真实状态变化；
6. 先做可复现的无界面内核，再做沙盘 UI；
7. 先验证命令延迟和认知隔离，再扩展战斗细节。

Commit 8 的完成条件为：

- 长平初始状态包含可追溯的历史事实、争议估计和独立的实验参数层；
- 玩家可以开始实时推进、下达延迟命令、派出侦察并看到 Belief State 更新；
- 战役可以在历史结果之外产生至少一个可解释的替代结果；
- 回放能够区分“史料约束”“玩家命令”“模拟假设”和“实时演化结果”；
- 试玩界面明确标注实验参数，不把未审定数字显示成确定史实。

Commit 9 已完成第一版实时战斗闭环：部队进入同一区域后形成接敌，按固定模拟间隔进行可复现的双方交换；部队状态会记录损耗、士气、疲劳、溃散或被歼，并将交战事件写入时间线。后勤系统按补给周期消耗 `supplyDays`，断粮后降低士气和准备度；这些状态变化均由通用内核驱动，不依赖 React 渲染循环。

长平战役已完成一次浏览器验收：命令传递、路线行军、到达、接敌和交战损耗能够连续出现；当前仍明确显示为受控模拟参数，不把相对战力指数解释为史实兵力。

Commit 10 对沙盘呈现边界进行了重新校准：加入营垒、壁垒、关口、道路、河谷和高地等静态地标符号；我方部队使用旗帜显示，敌军只从 `Belief State` 中的前线报告生成带可信度的疑似旗帜。原始交战交换不再出现在指挥官时间线或地图上，交战结果先经过延迟和可能错位的 `frontline-report` 才进入玩家认知。

Commit 11 已加入情报生命周期和敌方认知决策：每份报告记录来源、可靠度、可信度、有效时限和过期状态；报告过期后从沙盘中消失，但保留审计事件。敌方规则 AI 只读取敌方 `Belief State`，根据敌方收到的报告向报告区域机动，不读取玩家真实位置；敌方订单和敌方情报也不会混入玩家界面。

Commit 12 已完成第一版单局结算闭环：修正长平反向路线参数，接入任务目标、数据驱动胜负、胜负标题和安全战后复盘摘要，并将“坚守”作为第二类正式指令接入 Godot 客户端。长平现在可以在规则内核中于时间窗口内完成一局并返回不泄露敌军真值的指挥官视图。

Commit 13 已完成第一版前线报告误差反馈：侦察和接敌报告现在携带可信度、候选区域、误差半径和有效时间；报告抵达前会在界面显示“回传中”，抵达后才生成带误差范围的疑似敌情标记。Godot、浏览器验证面和回放协议使用同一份报告字段，真实敌军位置仍不会进入指挥官视图。

当前仍未完成的部分：敌方规则 AI 的编队、目标和反欺骗策略仍需深化，任务型命令还需要扩展到警戒、掩护、封锁、截粮、撤退和支援，战后复盘还需要加入认知变化与真实世界差异的专门模式；Godot 也仍需完成完整的 15—30 分钟单局节奏、平衡和可视化复盘。下一步优先扩展这些实时系统，而不是继续扩大长平资料文件数量。
