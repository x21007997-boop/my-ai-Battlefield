# 历史战争认知沙盘：产品与技术详细方案

## 0. 方案结论

本项目不做传统 RTS，也不做固定剧情式的历史关卡，而是建设一套：

> **以真实历史条件为起点、以信息不对称和认知博弈为核心、允许历史结果自由涌现的实时战争指挥沙盘。**

首个完整场景选择“长平之战”，但第一版不模拟整个战役的所有阶段，而是先选择一个可控的关键时间窗口，验证以下核心体验：

```text
玩家只能看到有限且可能错误的情报
→ 形成对战场的判断
→ 派出侦察、验证或制造假象
→ 下达有延迟的命令
→ 部队根据状态和指挥官能力执行
→ 战场持续演化
→ 新战报改变玩家认知
→ 战后复盘真实因果链
```

现有项目可以继续复用界面、剧本注册、存档分支、AI服务和测试体系，但不能直接把当前的月度政治回合引擎改成战争引擎。建议保留弘光剧本作为现有领域，新增独立的 `battlefield` 领域和连续时间模拟内核。

## 1. 产品定位

### 1.1 产品名称

工作名称：**历史战争认知沙盘**

英文内部名称：**Historical Battlefield Cognition Sandbox**

首个剧本：**长平之战：决战前的认知与指挥**

### 1.2 玩家身份

玩家不是士兵，也不是全知的上帝视角玩家，而是处于特定指挥层级的历史军队长官。

玩家主要负责：

- 判断敌军意图；
- 分配侦察和观察资源；
- 安排主力、侧翼、预备队和补给；
- 下达任务型命令；
- 处理战报、误报和失联；
- 选择是否使用欺骗和诱导；
- 在时间压力下承担战略后果。

玩家不直接负责：

- 点击每个士兵的移动路径；
- 每秒调整所有单位的站位；
- 直接读取敌军真实坐标；
- 通过升级数值解决所有问题。

### 1.3 与传统战争游戏的区别

传统战争游戏通常是：

```text
看见敌人 → 选择单位 → 下达命令 → 战斗结算
```

本项目的核心是：

```text
真实世界状态
→ 情报产生
→ 情报传播
→ 玩家形成认知
→ 玩家判断敌方意图
→ 下达命令和计策
→ 命令传播与执行
→ 世界状态改变
→ 新情报产生
```

玩家真正管理的不是单位数量，而是：

> **自己对战争的理解，以及敌人对战争的理解。**

## 2. 第一版目标与非目标

### 2.1 第一版必须验证的事情

第一版只需要验证四个问题：

1. 玩家是否愿意在信息不完整时做出判断；
2. 玩家是否能理解侦察、命令延迟和战场反馈之间的关系；
3. 玩家是否能通过计策改变敌方的判断；
4. 战后复盘是否能让玩家理解“自己为什么赢或输”。

### 2.2 第一版不做的事情

第一版明确不做：

- 几千个士兵的个体级模拟；
- 高精度 3D 战斗动画；
- 多人联机；
- 全长平战役所有阶段；
- 所有兵种和时代通用规则；
- 让大模型每秒参与战斗计算；
- 让 AI 直接决定世界状态；
- 精确到个位数的兵力和伤亡数据；
- 真实地图上的每一条村道和每一个居民个体。

第一版追求的是“足够真实，从而产生真实的指挥决策”，不是“把历史数据库全部搬进游戏”。

## 3. 核心体验设计

### 3.1 实时方式

游戏后台连续运行，但地图不需要每秒播放部队动画。

建议采用：

- 固定时间步长模拟；
- 事件驱动的界面刷新；
- 地图在关键态势变化时更新；
- 玩家可以随时发布命令；
- 命令不会瞬间生效；
- 关键战报可以触发自动暂停或提示。

第一版提供：

- 暂停；
- 1 倍速度；
- 2 倍速度；
- 4 倍速度；
- 关键事件自动暂停开关。

这仍然是实时模拟，不是回合制。暂停只是用于指挥和学习，不改变世界连续运行的规则。

### 3.2 一局时长

第一版单局目标：15—30 分钟。

玩家应该在前 5 分钟内：

- 看懂自己的任务；
- 看懂当前已经掌握的情报；
- 下达第一道命令；
- 感受到命令延迟或情报不确定性。

### 3.3 核心循环

```text
阅读战报
→ 形成敌情假设
→ 分配侦察
→ 等待或提前行动
→ 下达任务型命令
→ 观察命令传递和执行
→ 处理新的战报
→ 识别敌方计策
→ 调整主力、预备队和补给
→ 触发战斗结果
→ 战后查看三层战场和因果链
```

### 3.4 玩家真正要做的选择

玩家的主要决策应该是：

- 现在行动，还是继续侦察；
- 查北线，还是验证南线；
- 追击，还是保存体力；
- 主力压上，还是保留预备队；
- 守住阵地，还是主动迂回；
- 抢攻敌军，还是优先切断补给；
- 使用计策，还是保持真实部署；
- 相信一份战报，还是等待第二个独立来源。

## 4. 三层世界模型

这是本项目必须优先落地的底层设计。

### 4.1 历史事实层 Historical Data

描述史料、考古和地理研究能够确认或推定的内容：

- 战役时间范围；
- 参战方和将领；
- 战场地形；
- 道路、水系和城邑；
- 兵力范围；
- 后勤条件；
- 已经发生的历史事件；
- 当时可能获得的信息；
- 历史资料之间的争议。

该层不等于游戏中的实时状态，也不能直接被玩家读取。

### 4.2 世界状态层 World State

描述这一局游戏中真实发生的事情：

- 部队真实位置；
- 真实兵力和编制；
- 真实士气和疲劳；
- 真实补给余量；
- 真实命令状态；
- 真实侦察结果；
- 真实欺骗效果；
- 真实战斗和伤亡；
- 真实控制区域；
- 真实事件时间线。

正常游戏过程中，玩家和敌方 AI 都不能直接读取完整的 World State。

### 4.3 认知状态层 Belief State

每一个有决策能力的主体都拥有自己的认知状态：

- `playerBeliefState`：玩家当前认为战场是什么样；
- `enemyBeliefState`：敌方指挥官当前认为战场是什么样；
- `subordinateBeliefState`：部队和基层将领当前知道什么；
- `civilianInformationState`：村落、商人和地方势力知道什么。

地图默认只读取 `playerBeliefState`。

战后复盘才展示：

```text
玩家当时看到的战场
敌方当时看到的战场
真实发生的战场
```

## 5. 历史数据治理

### 5.1 四种数据类型

所有历史数据必须标明类型：

| 类型 | 含义 | 示例 |
|---|---|---|
| `historical_fact` | 史料或考古能够确认 | 某将领确实参与战役 |
| `historical_estimate` | 有依据但数值存在争议 | 兵力约 2.5—3.5 万 |
| `scenario_assumption` | 为了运行游戏对未知部分做的假设 | 某部队开局位于某区域 |
| `simulation_variable` | 由模拟器动态计算 | 当前士气、疲劳、命令执行度 |

不能把这四类数据混在一起。

### 5.2 证据等级

建议使用：

| 等级 | 含义 |
|---|---|
| `S` | 考古、遗址规划、可靠测绘或地理数据 |
| `A` | 主要史料直接记载 |
| `B` | 学术研究、地方志、可靠二手研究 |
| `C` | 地方传统或存在较大争议的资料 |
| `D` | 根据地形和历史约束做出的游戏推定 |
| `X` | 当前无法验证 |

示例：

```json
{
  "id": "qin-detachment-north",
  "name": "秦军北侧奇兵",
  "historicalStatus": "historical_estimate",
  "strength": { "min": 5000, "max": 9000, "unit": "人" },
  "sources": ["shiji-changping", "research-2024-01"],
  "evidenceGrade": "B",
  "exactRoute": {
    "status": "scenario_assumption",
    "note": "史料只确认其承担侧后任务，具体路线不确定"
  }
}
```

### 5.3 来源包

每个战役包必须有 `sources.json`，记录：

- 来源名称；
- 来源类型；
- 作者或机构；
- 年代；
- 可支持的事实；
- 争议和局限；
- 访问或查阅信息；
- 适用的数据字段。

AI生成的文字不能成为历史事实来源。

## 6. 战场状态模型

### 6.1 部队实体

第一版部队不模拟单兵，而模拟有指挥关系的编队：

```json
{
  "id": "zhao-center-01",
  "name": "赵军中央部",
  "side": "zhao",
  "commanderId": "zhao-commander-01",
  "location": { "areaId": "central-ridge", "certainty": 1 },
  "strength": { "current": 12000, "effective": 0.82 },
  "morale": 68,
  "fatigue": 24,
  "supplyDays": 4.5,
  "readiness": 0.78,
  "posture": "defensive",
  "currentOrderId": "order-0007",
  "communication": "delayed"
}
```

重点状态包括：

- 位置和位置不确定性；
- 编制和有效兵力；
- 士气；
- 疲劳；
- 补给天数；
- 行军或战斗准备度；
- 当前命令；
- 与指挥部的通信状态；
- 是否暴露；
- 是否被包围或切断。

### 6.2 将领实体

将领不能只用武力和智力表示，应包括：

- 风险偏好；
- 进攻倾向；
- 对情报的谨慎程度；
- 追击倾向；
- 预备队使用习惯；
- 对欺骗的敏感程度；
- 对伤亡的容忍度；
- 对补给的重视程度；
- 对上级命令的服从程度；
- 历史身份和政治约束。

这些属性影响将领如何理解命令和战报，而不是简单地给单位增加数值。

### 6.3 战场区域

第一版采用“区域—连接图”而不是逐像素地形：

- 山口；
- 高地；
- 河谷；
- 营地；
- 补给节点；
- 聚落；
- 观察点；
- 主要道路；
- 关键控制点。

每个区域拥有：

- 地形类型；
- 高程和坡度等级；
- 观察范围；
- 隐蔽能力；
- 行军成本；
- 防守优势；
- 补给通过能力；
- 可容纳部队规模。

这能先验证规则，再逐步接入更精细的 GIS 数据。

## 7. 实时模拟内核

### 7.1 模拟与渲染分离

模拟器不能依赖 React 的渲染循环。

建议结构：

```text
Simulation Worker
  └── 固定时间步长推进 World State

Main Thread
  └── 接收状态快照和关键事件
  └── 更新沙盘、战报和命令面板
```

模拟时间可以每 1 秒推进一次，界面只在以下情况刷新：

- 部队进入新区域；
- 侦察任务完成；
- 命令送达；
- 部队接敌；
- 补给线中断；
- 士气跨越关键阈值；
- 新战报抵达；
- 计策被发现；
- 目标控制权变化。

### 7.2 事件日志

每次状态改变都要记录事件：

```json
{
  "id": "event-0042",
  "simTime": 842,
  "type": "report_arrived",
  "source": "scout-north-01",
  "visibleTo": ["zhao-command"],
  "facts": ["观察到烟尘"],
  "interpretation": "可能有大规模部队移动",
  "confidence": "medium"
}
```

事件日志是：

- 实时 UI 的数据源；
- 战后复盘的数据源；
- 分支存档的数据源；
- 自动测试的数据源；
- AI 解释的数据源。

### 7.3 同一随机种子可复现

同一份：

- 历史剧本版本；
- 初始世界状态；
- 随机种子；
- 玩家命令；
- AI决策；
- 模拟器版本；

必须能够复现相同的关键结果。

## 8. 命令系统与指挥摩擦

### 8.1 命令不是单位移动点

命令采用任务型结构：

```json
{
  "id": "order-001",
  "issuer": "player",
  "recipient": "zhao-left-wing",
  "objective": "hold",
  "targetArea": "north-pass",
  "priority": "high",
  "constraints": ["不得主动追击"],
  "fallback": "撤至第二防线",
  "deadline": 900,
  "rawText": "左翼守住北口，不得追击，若敌军突破则退至第二防线"
}
```

### 8.2 命令生命周期

```text
草拟
→ 发送
→ 传递中
→ 部队收到
→ 将领理解
→ 执行中
→ 执行完成 / 部分执行 / 拒绝 / 失联
```

每一步都受到影响：

- 距离；
- 道路；
- 地形；
- 昼夜；
- 通信状态；
- 将领能力；
- 部队疲劳；
- 命令是否清晰；
- 是否与此前命令冲突。

### 8.3 自然语言解析

不建议让大模型直接产生最终命令。采用两层结构：

```text
自然语言
→ 结构化意图解析
→ 本地规则校验
→ 玩家确认
→ 进入命令队列
```

本地规则必须验证：

- 目标部队是否存在；
- 目标区域是否可达；
- 命令是否超出指挥层级；
- 是否有足够补给；
- 是否与已有命令冲突；
- 是否引用了玩家尚未掌握的信息。

## 9. 侦察、情报与认知

### 9.1 情报来源

第一版可以包含：

- 斥候；
- 骑兵侦察；
- 高地观察；
- 前哨；
- 村落；
- 商旅；
- 难民；
- 俘虏；
- 敌方旗号；
- 烟尘、火光和战斗声音；
- 补给线异常。

### 9.2 情报字段

```json
{
  "id": "intel-008",
  "sourceType": "scout",
  "sourceId": "scout-north-01",
  "observedAt": 620,
  "reportedAt": 710,
  "area": "north-valley",
  "observation": "发现大量烟尘和旗帜",
  "freshness": "new",
  "sourceReliability": "medium",
  "independenceGroup": "scout-network-north",
  "interpretation": "可能有敌军主力移动",
  "truth": "unknown"
}
```

### 9.3 情报不能简化成可信度百分比

玩家需要同时判断：

- 信息是否新鲜；
- 来源是否独立；
- 来源是否可能被敌方操纵；
- 不同报告是否指向同一事件；
- 信息是事实还是解释；
- 信息是否与已知地形和补给条件冲突。

界面可以显示“高、中、低”或可信区间，但不能让玩家只按一个数字排序。

### 9.4 事实与解释分离

高质量的情报设计不是系统无缘无故发送假信息，而是：

> 情报本身是真的，但玩家对情报的解释可能是错的。

例如：

```text
事实：敌军正在撤退。
错误解释：敌军已经溃败。
真实意图：敌军正在诱导我方追击。
```

## 10. 计策与欺骗系统

### 10.1 计策作用对象

所有计策优先作用于：

> **敌方的 Belief State 和决策权重。**

而不是直接提供攻击力加成。

### 10.2 第一版计策

优先实现：

- 假营地；
- 假旗号；
- 佯退；
- 隐藏预备队；
- 夜间调动；
- 故意泄露错误路线；
- 假运输队；
- 让敌方看到不完整部署。

### 10.3 计策必须有成本和反制

每项计策都要有：

- 执行成本；
- 所需部队或资源；
- 生效时间；
- 敌方发现条件；
- 失败后的反噬；
- 对敌方认知的具体影响。

计策流程应该是：

```text
制造假象
→ 敌方首次观察
→ 敌方形成判断
→ 敌方采取行动
→ 敌方进行二次验证
→ 怀疑或确认
→ 反制或继续受骗
```

### 10.4 计策公平性

玩家正常游戏时不能直接看到计策是否成功。

但战后必须解释：

- 敌方看到了什么；
- 哪个假象被相信；
- 哪次验证暴露了问题；
- 计策如何改变敌方行动；
- 如果不使用计策会怎样。

## 11. 后勤、士气、疲劳和社会地形

### 11.1 后勤

粮草不能只是库存数字，而应当表现为可持续行动能力：

- 当前可维持天数；
- 主要补给路线；
- 运输节点；
- 路线容量；
- 路线安全度；
- 补给抵达时间；
- 失去补给后的影响。

第一版只模拟关键节点和主要路线，不模拟每一辆粮车。

### 11.2 士气

士气由多种因素共同产生：

- 连胜或连败；
- 伤亡；
- 疲劳；
- 饥饿；
- 主将状态；
- 援军消息；
- 被包围；
- 与指挥部失联；
- 对敌军规模的认知；
- 周围友军状态。

士气必须同时受到真实状态和错误认知影响。

### 11.3 疲劳

强行军、连续战斗和缺粮会造成：

- 移动速度下降；
- 侦察能力下降；
- 命令执行变慢；
- 战斗能力下降；
- 士气恢复变慢；
- 掉队和失联增加。

### 11.4 社会地形

村落、商人、猎户、驿夫和难民不需要作为大量独立角色模拟，但应作为信息和后勤网络节点存在。

第一版只需要模拟：

- 信息来源可靠度；
- 消息传播延迟；
- 粮草或民夫可用性；
- 对敌我双方的倾向；
- 是否被强制、收买或欺骗。

## 12. 敌方 AI

### 12.1 信息边界

敌方 AI 严禁读取完整 World State。

AI 只能读取：

- `enemyBeliefState`；
- 已收到的敌方情报；
- 自己部队的反馈；
- 自己的战略目标；
- 将领人格和作战倾向；
- 已经确认的玩家行动。

### 12.2 AI 分层

建议分为三层：

1. **目标层**：控制高地、切断粮道、保存主力等；
2. **计划层**：主攻、佯攻、迂回、撤退、诱敌等；
3. **执行层**：部队移动、侦察、部署和战斗。

第一版目标层和执行层使用规则 AI，计划层可以使用有限结构化 AI 建议。

大模型只在以下时机调用：

- 收到重要情报后；
- 计划需要重新评估时；
- 将领需要作出性格化判断时；
- 战后需要生成解释时。

不能把大模型放进每秒循环。

### 12.3 将领人格

同一份情报，不同将领可以得出不同结论：

- 谨慎型：要求第二来源验证；
- 激进型：认为战机稍纵即逝；
- 保守型：优先保住补给；
- 猜疑型：容易怀疑假象；
- 政治型：更在意上级和国内压力。

这比“武力 96、智力 97”更重要。

## 13. 战略目标与历史分歧

### 13.1 多层胜利目标

战争不能只有“歼灭所有敌军”。目标至少包括：

- 守住关键区域；
- 保住补给线；
- 保存主力；
- 迫使敌军撤退；
- 延缓敌军推进；
- 取得决定性战果；
- 在较低损失下完成任务。

可能出现：

> 战术失败，但战略成功。

### 13.2 历史事件不是硬编码

不能简单写成：

```text
第20日一定发生某次换将
```

而应写成条件集合：

```text
长期无战果
+ 国内压力上升
+ 现任将领失去支持
+ 敌方信息操作成功
→ 改变主将的概率上升
```

历史事件可以自然产生，但首个剧本也应保留历史锚点，避免完全脱离时代条件。

### 13.3 历史分歧点

系统记录真实历史与当前世界线首次不同的地方：

```json
{
  "simTime": 1420,
  "historicalEvent": "赵军主帅发生变化",
  "currentOutcome": "主帅未变化",
  "reasons": ["前线取得局部战果", "朝廷压力较低"]
}
```

## 14. 战后复盘

战后复盘不是普通录像，而是因果解释系统。

### 14.1 三张地图

同时展示：

1. 玩家当时看到的地图；
2. 敌方当时看到的地图；
3. 真实世界状态地图。

### 14.2 决策因果链

```text
北线侦察不足
↓
错误判断敌军意图
↓
预备队提前前移
↓
补给线暴露
↓
敌军完成迂回
↓
补给中断
↓
士气下降
↓
中央防线崩溃
```

### 14.3 复盘必须回答的问题

- 玩家在当时知道什么；
- 哪些信息后来被证明错误；
- 哪个命令产生了延迟；
- 哪个部队没有按预期执行；
- 敌方什么时候发现玩家意图；
- 哪次计策成功或失败；
- 最早可以改变结果的决策点在哪里；
- 如果采取另一方案，可能出现什么结果。

## 15. 长平首个剧本设计

### 15.1 选择原则

首个可玩版本的战役窗口应满足：

- 时间范围清晰；
- 战场空间可压缩成有限区域；
- 参战部队数量可控制；
- 有明确的侦察和后勤问题；
- 有至少两种合理战略；
- 能产生历史结果和替代结果；
- 史料来源和争议能够被记录。

### 15.2 第一版规模

- 1 张战场沙盘；
- 6—10 支主要部队；
- 2 方指挥体系；
- 2—4 名关键将领；
- 6—8 个战场区域；
- 4—6 条主要道路或补给连接；
- 3—5 个关键聚落或信息节点；
- 3 个战略目标；
- 5—8 种命令；
- 3—5 种侦察行动；
- 3—5 种欺骗行动；
- 1 个规则式敌方 AI；
- 1 个战后因果复盘。

### 15.3 第一版战役目标示例

玩家一方可以拥有：

- 保住关键通道；
- 保持主力可战状态；
- 维持补给若干天；
- 阻止敌军完成包围。

敌方可以拥有：

- 切断关键粮道；
- 迫使对方离开防线；
- 形成局部优势；
- 在规定时间内取得战略突破。

具体历史数值和地理位置必须在数据考据后确定，不能在技术方案中先写死。

## 19. 第一版验收标准

满足以下条件，才算完成首个可玩原型：

### 实时性

- 世界状态连续推进；
- 玩家可以随时下令；
- 命令存在可观察的传递延迟；
- 关键事件可以自动暂停或提示；
- 地图不是按回合整体跳变。

### 认知边界

- 正常游戏不能读取敌军真实位置；
- 玩家地图读取的是 Player Belief State；
- 敌方 AI 读取的是 Enemy Belief State；
- AI 服务请求中不能包含不该看到的真实状态。

### 情报

- 至少三种情报来源；
- 情报有发生时间和到达时间；
- 情报有新鲜度和来源可靠性；
- 情报之间可以冲突；
- 玩家能够通过侦察改变认知，而不是直接获得答案。

### 指挥

- 至少五种任务型命令；
- 命令包含目标、约束和优先级；
- 部队可能延迟、部分执行或误解命令；
- 玩家不能直接微操单兵。

### 计策

- 至少三种计策；
- 计策改变敌方认知；
- 计策有成本；
- 敌方可以验证和识破；
- 战后可以解释计策的影响。

### 历史与复盘

- 每个关键初始数据有来源或证据等级；
- 历史事实、估计、假设和模拟变量分开；
- 战后展示三层地图；
- 有决策因果链；
- 可以记录第一个历史分歧点；
- 同一数据和种子可以复现结果。

## 20. 主要风险与应对

### 风险一：历史资料不够精确

应对：

- 用范围和可信度，不伪造精确数字；
- 公开数据争议；
- 将假设写入剧本；
- 战后区分历史事实与模型推定。

### 风险二：实时沙盘变得被动

应对：

- 命令有截止窗口；
- 战报持续到达；
- 关键态势自动提醒；
- 侦察和行动存在机会成本；
- 允许主动制造情报事件。

### 风险三：玩家觉得计策结果不可理解

应对：

- 计策必须有前置条件；
- 观察线索要逐步出现；
- 计策失败有可解释原因；
- 战后公开敌方认知变化。

### 风险四：AI作弊或产生幻觉

应对：

- AI只读取受控 Belief State；
- AI只能输出结构化建议；
- 本地规则引擎校验并执行；
- 事实数据不由 AI 生成；
- 没有 AI 时使用确定性规则 AI 继续运行。

### 风险五：范围快速膨胀

应对：

- 第一版只做一个战役窗口；
- 先做区域图，不做逐兵路径；
- 先做关键部队，不做全军；
- 先做三类信息和三类计策；
- 先验证“判断—侦察—欺骗—复盘”闭环。
